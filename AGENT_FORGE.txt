MASTER PROMPT — AGENT FORGE
Build a Local-First AI Agent Capability Engineering Platform

Version: 1.0
Implementation language: Python
Distribution model: Local-first CLI
Change policy: Approval-first
Primary objective: Analyze, curate, compose, upgrade, validate, and safely manage AI-agent capabilities across arbitrary software projects.

1. YOUR ROLE AND MISSION

Act as a principal software architect, Python engineer, developer-tools engineer, AI-agent infrastructure specialist, security engineer, and technical project maintainer.

Your task is to build Agent Forge: a local-first platform that improves the AI-agent infrastructure of existing software projects by selecting and applying relevant capabilities from curated sources.

The initial upstream sources are:

REA — https://github.com/morluto/rea
Everything Claude Code (ECC) — https://github.com/affaan-m/ECC
UI UX Pro Max — https://github.com/nextlevelbuilder/ui-ux-pro-max-skill

These are independent capability sources, not the core architecture of Agent Forge.

Agent Forge must eventually support additional repositories, internal skills, engineering standards, and agent platforms without requiring architectural redesign.

The product must work with both:

New projects that have little or no AI-agent configuration.
Existing projects that already contain carefully maintained instructions, skills, agents, hooks, MCP configuration, or other agent-related files.

The most important use case is upgrading an existing project's AI-agent system without damaging its existing engineering workflow.

Build a working, testable software product.

Do not stop after generating documentation, cloning repositories, or proposing an architecture.

2. ARCHITECTURAL DECISIONS — DO NOT CHANGE WITHOUT JUSTIFICATION

Use these decisions as fixed constraints.

2.1 Python

Build the CLI and core engine in Python.

Use a modern, maintainable Python project layout with:

pyproject.toml
Type hints.
Clear module boundaries.
Structured error handling.
Automated tests.
Reproducible development dependencies.
A documented installation and execution workflow.

Choose stable, actively maintained dependencies only when they provide meaningful value.

A reasonable initial stack is:

Typer for CLI commands.
Rich for terminal output.
Pydantic for structured models and validation, where appropriate.
PyYAML for human-editable YAML metadata.
pytest for testing.
Ruff for linting and formatting.
SQLite for local transaction and operational metadata when persistence is required.

Verify dependency compatibility before choosing versions. Avoid introducing unnecessary frameworks.

Do not build a web server or cloud service for the initial release.

2.2 Local-first

The product runs on the user's machine.

It must not require:

A hosted backend.
A remote database.
A central account.
A cloud registry.
A continuously running service.

The system may access Git repositories when the user requests source synchronization.

The system must not upload project source code, credentials, scan reports, or capability data to a remote service as part of its normal operation.

If an AI model or external integration is later introduced, document its data flow explicitly. Do not assume that local execution guarantees that all processed information remains local.

2.3 Approval-first

Default behavior must be non-destructive.

The default workflow is:

SCAN → ASSIGN → PLAN → DIFF → APPROVE → APPLY → VALIDATE

Commands that inspect projects must not modify them.

Commands that recommend or plan changes must not modify them.

Only an explicit apply operation may perform approved writes.

Approval must be bound to a specific plan and its contents. If the target project, plan, registry, or relevant source files change after planning, invalidate or revalidate the plan before applying it.

Never let a generic --yes flag silently bypass safety checks or authorize global configuration changes.

2.4 Independent target projects

Agent Forge must be usable from a workspace outside the target project.

For example:

/Users/example/agent-forge

Target:

/Users/example/projects/my-saas

The user must be able to run Agent Forge against the target without moving that project into the Agent Forge repository.

The target project's Git repository, ownership, dependencies, and existing configuration must remain independent.

4. PRODUCT PRINCIPLES

All design and implementation decisions must follow these principles.

4.1 Source-agnostic

REA, ECC, and UI UX Pro Max are initial sources.

The engine must operate on the capability registry, not hard-coded repository-specific logic.

Adding a new source must not require rewriting the scanner, matcher, planner, or apply engine.

4.2 Project-aware

Never assign capabilities simply because they are available.

Recommendations must account for:

Project type.
Language and framework.
Existing agent infrastructure.
User requirements.
Agent platform.
Dependencies.
Security restrictions.
Existing equivalent capabilities.
Compatibility and maintenance cost.
4.3 Additive by default

Prefer adding a new, isolated capability over rewriting a shared instruction file.

When a shared file must change, generate a minimal, reviewable patch.

Preserve unrelated content, formatting, comments, ordering, and user-owned instructions wherever practical.

4.4 Explainable recommendations

Every recommendation must explain:

Why it applies.
What problem it solves.
What already exists.
What it will add or change.
Dependencies and compatibility.
Potential conflicts.
Risk level.
How the result will be validated.
How the change can be reversed.

Do not rely solely on an LLM's subjective judgment. Use explicit rules and verifiable metadata wherever possible.

4.5 Provenance

Every curated capability must have traceable origins.

Distinguish:

Original upstream content.
Adapted content.
Workspace-created content.
Generated project-specific content.
User-modified installed content.

Never invent repository revisions, licenses, compatibility claims, or validation results.

12. CLI COMMAND SPECIFICATION

Build a consistent CLI using Typer or another justified Python CLI framework.

Use agent-forge as the command name.

Support useful help output, stable exit codes, readable errors, and machine-readable JSON output where appropriate.

12.1 Initialization

agent-forge init

Initialize the Agent Forge workspace, configuration, registry, and local state.

Requirements:

Detect existing workspace state.
Be safe to rerun.
Avoid overwriting user files.
Validate the resulting structure.
Explain what was created.
12.2 Source management

agent-forge sources list

List registered sources, revisions, and synchronization state.

agent-forge sources sync

Fetch approved upstream updates when requested.

Do not silently curate, install, or apply upstream changes.

12.3 Catalog

agent-forge catalog

List curated capabilities.

Support filters for category, platform, project type, status, and source.

agent-forge catalog show CAPABILITY_ID

Display capability metadata, provenance, dependencies, conflicts, and compatibility.

12.4 Scan

agent-forge scan PATH

Scan the target project and generate a profile/report.

Default behavior is read-only.

Support an explicit report destination without writing into the target project by default.

12.5 Assign

agent-forge assign PATH

Analyze the target and recommend capabilities.

Generate a versioned upgrade plan.

Do not modify the target.

Allow explicit user preferences or project constraints where appropriate.

12.6 Upgrade

agent-forge upgrade PATH

Compare currently managed capabilities with the curated registry.

Detect:

Outdated managed capabilities.
Registry changes.
Local drift.
Missing dependencies.
New conflicts.
Potential improvements.

Generate a plan rather than applying changes.

Do not update every capability simply because a newer version exists.

12.7 Diff

agent-forge diff PLAN_ID

Display exact proposed additions, modifications, and removals.

For shared files, show meaningful contextual diffs.

Identify operations that require additional approval.

12.8 Apply

agent-forge apply PLAN_ID

Apply an explicitly approved plan.

Before writing:

Validate the plan schema.
Verify the target identity.
Verify the plan has not become stale.
Recheck file hashes and destination paths.
Detect unexpected user modifications.
Validate capability dependencies.
Check authorization for each operation.
Create recoverable transaction metadata.
Confirm that each operation is within the approved scope.

Present a clear summary of changes before applying them.

Require explicit confirmation by default.

A previously approved plan may be applied non-interactively only if its identity, scope, hashes, and approval policy remain valid.

A plan must not grant permission to modify files or locations outside its recorded scope.

12.9 Validate

agent-forge validate PATH

Validate:

Registry and manifest integrity.
Managed capability references.
Destination files.
Dependency resolution.
Duplicate capabilities.
Relevant configuration syntax.
Adapter compatibility.
Recorded transaction integrity.

Do not run arbitrary project scripts without explicit authorization.

12.10 Status

agent-forge status PATH

Report:

Installed managed capabilities.
Versions and provenance.
Drift.
Outdated capabilities.
Conflicts.
Validation state.
Recent transactions.
12.11 Rollback

agent-forge rollback TRANSACTION_ID

Reverse changes managed by the selected transaction.

Before rollback:

Verify transaction integrity.
Compare current files against the expected post-apply state.
Identify independent user modifications.
Refuse unsafe overwrites.
Explain any conflicts.

Rollback must never blindly restore a historical file over subsequent user work.

12.12 Command consistency

All commands must:

14. SAFE FILE APPLICATION

Treat filesystem safety as a core feature.

14.1 File ownership

Track:

Files created by Agent Forge.
Files modified by Agent Forge.
Original content or a suitable recoverable baseline.
Installed capability IDs and versions.
Destination mappings.
Transaction identifiers.

Distinguish Agent Forge-managed files from user-owned files.

14.2 Shared configuration

Files such as CLAUDE.md and AGENTS.md require special handling.

Never replace the entire file simply to add a small instruction.

Prefer:

Separate skill files.
Clearly scoped additive sections.
Minimal contextual patches.
Explicit merge strategies.

If the system cannot determine a safe merge, stop and ask the user.

Do not silently delete or reorder unrelated user instructions.

14.3 Filesystem boundaries

Protect against:

Path traversal.
Absolute paths outside approved destinations.
Symlink escapes.
Stale plans.
Concurrent modifications.
Unexpected file types.
Partial writes.
Corrupted transaction records.

Use atomic writes where practical.

Do not follow symlinks into unrelated directories.

Revalidate the destination immediately before writing.

Do not delete user-owned files by default.

14.4 Rollback integrity

Store enough information to reverse managed changes.

Use content hashes and transaction records.

If a file has changed independently after installation, do not overwrite it during rollback.

Stop and present a recovery recommendation.

Do not promise successful rollback when safe recovery cannot be established.

Do not modify:
