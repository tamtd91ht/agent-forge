# ADR-0001: Architecture decisions for Agent Forge v0.1

Status: accepted (2026-10-16). Supersedes nothing.

## Context

Agent Forge improves the AI-agent infrastructure of arbitrary projects by installing curated
capabilities from untrusted upstream repositories. The master prompt fixes Python, local-first
and approval-first as constraints. Everything below records the choices made within them,
with the evidence that drove each one.

## Decisions

### D1. Workspace = directory with `agent-forge.yaml`; targets are always external

Resolution order: `--workspace` > `$AGENT_FORGE_HOME` > walk up from cwd > `~/.agent-forge`.
The target project is never moved or symlinked into the workspace; every write to it goes
through one path resolver (`apply/filesystem_safety.py`).

### D2. Registry on disk is the source of truth; SQLite is only an index

Plans and transactions are JSON documents (reviewable, hashable, diffable). SQLite
(`state/agent-forge.sqlite3`) indexes them for listing and is rebuilt by `reindex`.
Reason: integrity properties are easier to reason about on immutable documents, and losing
the index loses nothing.

### D3. Capability manifest is a Pydantic model; JSON Schema is exported from it

`registry/schema/*.schema.json` are generated by `scripts/export_schemas.py`. The model is
`extra="forbid"`, so unknown fields fail loudly. Manifests must live in a directory named
after their `id`.

### D4. Install strategies: `file_copy`, `section_merge`, `native_plugin`, `reference_only`

Evidence: REA's only user skill needs an MCP runtime; UI UX Pro Max's full toolkit needs an
installer. Modelling those as `native_plugin` lets the matcher *recommend with install hints*
without Agent Forge executing anything. `reference_only` informs recommendations only.

### D5. Shared files are never rewritten; only marker-delimited sections are managed

`<!-- agent-forge:begin id=… -->` / `<!-- agent-forge:end id=… -->`. Everything outside the
markers is preserved byte-for-byte. Any operation on a shared file needs
`approve --shared-files`. Rollback removes just the section when the rest of the file changed.

### D6. Approval is bound to a content digest

`Plan.content_digest()` covers target identity, registry digest, selected capabilities and
every operation (path, kind, content hash, before/after hashes). `apply` refuses a plan whose
digest no longer matches its approval, whose registry digest changed, or whose destination
files no longer hash to `before_sha256`. `--yes` only skips the interactive prompt.

### D7. Deterministic transaction id per plan

`tx-<plan suffix>`. This lets the managed manifest (`.agent-forge/managed.json`) be computed
at plan time and covered by the approval digest; `installed_at` is the only field stamped at
apply time. A plan can therefore be applied at most once.

### D8. Managed state lives in the target (`.agent-forge/managed.json`) and in the workspace

The target copy makes the project self-describing for other machines and is validated, never
trusted blindly (schema + unsafe-path checks). The workspace keeps transactions and backups.

### D9. Hooks and MCP are not installable kinds in v0.1 — superseded by D13

Both execute code (hook commands, MCP server processes). Upstream hooks (ECC) write under
`~/.claude` and probe the network. v0.1.0 excluded them entirely; D13 adds them behind
dedicated approval classes.

### D13. Approval classes: `standard`, `shared_file`, `hook`, `mcp`

Every `FileOperation` carries an `approval_class`. `approve` grants classes explicitly
(`--shared-files`, `--hooks`, `--mcp`); `apply` refuses any operation whose class was not
granted; `forge` asks per class or leaves ungranted capabilities out of the plan at build
time (`MatchContext.allowed_classes`), so the managed manifest never lists them.

Hooks and MCP servers are installed as **JSON fragments** (`apply/jsonmerge.py`) merged into
`.claude/settings.json` / `.mcp.json`: deep-equal hook groups are appended once, MCP servers
are set by name and a name clash with a different config is a planning error. Removal and
rollback delete exactly the merged entries, so user-added hooks/servers survive. Upstream
hook scripts are still excluded; the shipped hooks are workspace-authored, dependency-free,
act on the single edited file, and no-op when their tool is missing.

Operations on the same path are chained in plan order (planner cache, pre-flight projection,
diff rendering), which is what allows several capabilities to share one settings file.

### D10. Codex gets only skills and AGENTS.md sections

Verified: `.codex/*` layers load only for trusted projects and need per-hash hook trust;
there is no path-scoped rule concept. Forcing parity would ship files Codex ignores or
mis-trusts. Rules and agents are reported as "requires adaptation" on Codex.

### D11. Matching = hard rules first, then scoring

Rules reject on status, platform, applicability, already-installed, equivalents,
destination collisions, declared conflicts and missing dependencies. Scoring only ranks the
survivors and decides recommended vs optional. No LLM in the loop.

### D12. Curation is scripted but judged by hand

`scripts/curate.py` copies an explicit file list from a pinned revision and writes license
notices; the manifest (purpose, applicability, equivalents, risk, rationale) is hand-written.
Re-running the script after `sources sync --update` surfaces upstream changes as a plain
`git diff registry/`.

## Consequences

- Adding a source = add to `sources.yaml`, add curation items, write manifests. No engine code.
- Adding a platform = one adapter class (detect, inventory, allowed roots, format rules).
- The approval model makes plans single-use; re-planning is cheap (read-only) so that is fine.
- Symlink tests skip where symlinks cannot be created; junction tests cover Windows.
