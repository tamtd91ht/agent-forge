## Reviewer notes (2026-10-29, added after the run; not part of the generated report)

- **What the task measures:** adherence to the house style (semantic tokens instead of raw
  colours or Tailwind's default palette, a success token defined in a theme file and used by
  the create action, an empty-state branch). It does not measure whether the screen is better
  for users. The prompt does not mention design, as a real request would not.
- **Why baseline failed:** all three runs built a working page with an empty state and failed
  only on default-palette utilities (`bg-blue-600`, `text-gray-500`, …) and the missing success
  token.
- **What candidate did (kept copies inspected):** defined the OMICX tokens for light and dark in
  `app/globals.css`, mapped them in `tailwind.config.js` as `references/stack-mapping.md`
  describes for Tailwind v3, used `rounded-card` / `rounded-medium` / `rounded-tiny`, one
  `bg-success` create action, a labelled search field and two empty states.
- **Confound:** the candidate arm is `forge --request forge.rule.omicx-ui`, which installs the
  whole recommended set for the fixture (ECC web / React / TypeScript rules and skills,
  reviewers, uiux.guidelines …), not only the rule and its skill. The result is "Agent Forge
  with the house style" versus nothing; it also shows the rule's precedence held against
  `ecc.rules.web` `design-quality.md`, which was installed in every candidate run.
- **Missing metrics:** two runs (baseline 2, candidate 1) have no tokens or cost because the
  harness decoded the tool's UTF-8 output with the Windows code page; fixed in
  `agent_forge_eval/harness.py` after this run. Pass / fail is unaffected (acceptance runs
  separately).
- **Size:** one task, three runs per arm; the intervals are wide. The `review.evidence` entry
  needs a human `decided_by` and is left to the maintainer.
